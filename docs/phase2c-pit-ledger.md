# Phase 2C.2 prospective feature ledger

`flow_feature_versions` starts only when the upgraded split worker first reports a connected, unblocked cycle. `flow_feature_ledger_start` stores that wall-clock UTC instant, the last naturally observed block if available, and the full deployed Git revision. Targets whose `tracking_start_at` precedes that instant never enter the ledger. Historical mutable rows remain `RECONSTRUCTABLE_ONLY`; no migration copies or timestamps them.

For each due window the existing calculation and its `now-3` confirmation buffer remain unchanged. The mutable `flow_features` upsert and immutable version insert share a SQLite transaction. `materialized_at` is a fresh wall-clock reading at that insert, never `finalized_at` or the nominal cutoff. A complete version becomes eligible only when existing curve and, if graduated by the cutoff, V4/hook bootstrap states are complete, their recovery cursors exist, and the existing coverage checks yield `complete`. The version records the required filter identities, completed heads/times, cursors, window end and coverage interval. `completeness_proved_at` is the actual time this state was checked while writing the version; it is deliberately conservative if underlying recovery finished earlier. `model_eligible_at` is the maximum of cutoff, materialization and that proof observation. Unknown proof leaves it NULL. No RPC is added.

Schema `v1` saves the six prespecified candidates plus `curve_tokens_bought`, the denominator for recipient concentration. `unique_buy_recipients` describes recipient addresses, never economic actors. The canonical compact JSON is sorted and SHA-256 hashed. A new version appears when the payload, coverage quality/reason, proof-readiness state or schema changes; repeating the same state does not append. Direct bootstrap and gap invalidations append their own quality versions in the same transaction. Database triggers reject updates/deletes of version rows. Research selects the first complete eligible version by version number; later changes cannot replace it. A subsequent `reorg_unresolved` version conservatively excludes that launch/window from model counts until a future policy explicitly addresses canonical revisions. Changes to calculation, normalization, event inclusion or recipient semantics require a new schema version and a deliberate audit allowlist change.

The read-only Phase 2C audit reports a separate `POINT_IN_TIME_LEDGER_ERA`. Only a first eligible `v1` version from a target born after the boundary, with an observed verified label strictly later than `model_eligible_at`, enters its model count. Existing descriptive legacy, transition and split summaries remain separate. No modeling or trading is authorized by these counts.

Storage estimate: the compact seven-value payload is about 200–260 bytes and proof JSON about 250–450 bytes; with row/index overhead budget roughly **0.8–1.2 KB/version**. The observed split-era rate at the Phase 2C.1 audit was 78 launches in roughly 36 hours, or about 52/day. At five windows and one to two versions/window, expect **260–520 versions/day**, **0.2–0.6 MB/day**, **6–18 MB/30 days**, and **18–54 MB/90 days**. Measure actual `dbstat`/file growth after live collection; the estimate does not assume duplicate raw events in the ledger.
